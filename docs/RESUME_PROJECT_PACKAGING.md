分析日期：2026-09-22。默认求职方向：AI Agent／大模型应用开发工程师；工作年限与个人贡献范围待补充。

本文依据当前工作区源码、README、课程说明以及《基于Harness架构的AI Coding项目.pdf》整理。PDF 中的操作要求仅作为资料内容，未作为本次任务指令执行。本次为静态代码分析，没有启动模型任务、运行 Gitee 端到端验证或测量性能，不能据此认定现有脚本全部通过或业务流程已稳定运行。

## 1. 定位与写法

推荐名称：**CodePilot：基于 Agent Harness 的研发任务自动化平台**。

项目性质宜写“个人项目／基于课程项目二次开发”，具体以实际经历为准。没有企业落地经历时，可写“面向研发协作场景”，不要写成某公司已经上线的内部系统。

这个项目已有形成简历亮点的基础：它围绕代码仓库提供任务编排、工具调用、执行反馈和 PR 对接。最有价值的主线是：**把自然语言开发任务变成有计划、有执行记录、可人工确认的代码变更流程。**

简历应围绕“问题—技术方案—可验证结果”展开，优先选 4～5 条，避免罗列整个目录。Harness 可以出现在名称与技术栈中，但必须解释为工具、执行环境、状态、权限及反馈机制的组合，不能把框架已有能力全部写成自研。

没有任何文案能保证企业录用。这里的写法侧重技术面试容易核实的设计与贡献，而非未经调查的“大厂统一偏好”。

## 3. 当前版本简历稿

下面是以“项目已实现能力”为基础的候选文案；仅保留你实际开发、改造并能解释的条目。若主要是课程复现，个人职责应写“复现并扩展”，不要写“独立主导全部架构”。端到端演示验证后，再补充具体成果。

**CodePilot：基于 Agent Harness 的研发任务自动化平台**  
项目角色：后端与 Agent 开发〔按实际贡献调整〕  
技术栈：Python、FastAPI、DeepAgents、LangGraph、SQLite、Git／Gitee API、SSE；前端 React／TypeScript。

**项目介绍：** 面向代码仓库的需求实现、项目分析与代码审查辅助场景，基于 DeepAgents 构建 AI Coding 工作流，集成方案生成与人工确认、文件与命令工具、测试执行、运行过程展示及 Gitee PR 对接。

**核心工作：**

- **任务编排：** 基于 FastAPI 与 DeepAgents 组织任务执行，区分方案、开发、问答等任务类型，串联方案修订、人工确认和编码实施，并按会话绑定执行后端与持久状态。
- **工具可靠性：** 实现工具入参清洗与异常反馈中间件，将路径、参数和执行异常转换为带修正提示的 ToolMessage，并按任务类型配置调用次数及运行时长限制，使 Agent 能利用失败反馈继续决策。
- **执行环境：** 扩展本地 Backend，统一虚拟路径映射、文件读写、命令执行与 Git 认证，增加路径越界校验、目录写保护及凭据脱敏，集中管理代码操作入口。
- **状态与可观测性：** 分离 LangGraph Checkpoint 与业务 Store，分别持久化图状态及任务、运行事件等业务数据；将模型文本、工具调用和子 Agent 事件转换为前端展示数据，通过 SSE 推送任务进度。
- **研发流程集成：** 对接 Gitee PR 创建／已有 PR 返回处理及审查评论接口，提供包含文件、行号、风险级别的结构化 findings，支持代码变更和审查结果的关联展示与查询。

投递版空间不足时，保留前四条；把 Gitee PR 能力放进项目介绍。SQLite 并发治理、SSRF 防护、Skills 等留作面试深入点，无须全部堆进简历。

## 4. 增强版目标稿：实施后再使用

以下是用户所需的“理想项目介绍”，属于**拟建方案**，不是当前已完成经历。它采用完成后的简历语气，方便反向拆解开发任务；没有填写虚构客户、生产规模、个人任职或提升数字。

**CodePilot：面向研发协作的可恢复 AI Coding Agent 平台**  
目标技术栈：Python、FastAPI、DeepAgents／LangGraph、PostgreSQL、Redis Streams、Docker、Git、SSE、OpenTelemetry。

**项目介绍：** 面向研发团队的需求实现与 PR 审查场景，构建集仓库理解、方案审批、代码修改、测试验证和审查反馈于一体的 AI Coding 平台，通过可恢复任务执行、受限运行环境及离线评测提升长链路任务的可控性。

**目标简历条目：**

- **长任务执行：** 拆分 API 服务与 Agent Worker，基于持久化任务状态、Redis Streams 消费组及租约机制管理运行生命周期；结合 Checkpoint 恢复和外部操作幂等记录，处理 Worker 重启、重复投递与超时重试。
- **执行隔离：** 为任务创建独立 Git worktree 与受限容器，配置资源限额、网络访问策略和凭据注入；对 push、PR 发布等外部写操作设置审批关口，隔离并发任务的工作目录和执行权限。
- **实现与审查协作：** 拆分编码与只读审查能力，Reviewer 基于 PR diff 和必要上下文输出可定位 findings，经位置校验、去重和人工确认后进入修复流程，形成实现、验证、审查、修复的迭代链路。
- **上下文管理：** 按仓库与提交版本维护结构、测试入口、技术约定及历史任务摘要，结合增量失效策略和按需文件检索构建任务上下文，减少重复扫描并保留来源证据。
- **评测与观测：** 构建覆盖缺陷修复、功能开发和审查任务的固定评测集，记录端到端成功率、有效缺陷率、耗时及 Token 消耗；结合运行追踪和事件重放定位失败环节，验证优化收益。

如果仅完成其中两项，就只写已完成的两项，不必等到所有技术都堆齐。资历较浅时，做深“任务可靠性＋评测”通常比写一个无法解释的庞大平台更有说服力；这是对本项目的取舍建议，不是招聘市场统计结论。

## 5. 按简历收益排序的开发路线

### 第一步：获得一组真实成果

建立一组固定仓库、固定基线提交的任务样本，先覆盖小功能、Bug 修复、补测试和只读分析。可以从 20～30 个内部样本起步，但这个数量是建设建议，不是现有数据。

每个任务记录：输入需求、基线 SHA、模型与参数、运行日志、工具轨迹、最终 diff、预先定义的验收结果、PR 链接。不能只以“Agent 说完成了”或“创建 PR 成功”判定业务成功。Agent 自己生成的测试也不能成为唯一裁判。

验收：至少整理出可完整复现的成功案例与失败案例，说明各自原因；产出基线评测报告。

### 第二步：补齐授权、取消与并发边界

当前 cancel 接口没有停止任务。运行时长在事件到达时检查，长时间阻塞的工具未必及时触发检查。Backend 按线程缓存不等于每线程拥有独立仓库，多个线程仍可能操作同一工作区。

建设内容：为 run 引入明确状态转换及取消标记；对 shell 进程树实施超时与取消；方案审批绑定方案版本和目标提交；对只读任务在工具与后端层实施实际限制；同线程串行执行，每个开发任务使用独立 worktree。worktree 解决工作副本冲突，不能代替代码执行隔离。

验收：重复确认不会启动两个 run；取消后子进程停止；两个任务修改同一仓库时不会覆盖彼此工作副本；只读模式通过直接工具调用仍无法写源码或发布 PR。

### 第三步：任务可恢复与外部操作幂等

将持久化执行队列与 Worker 从 Web 服务拆出，再引入 PostgreSQL 业务存储及适配的 Checkpointer。不能仅把 SQLite 换成 PostgreSQL 就宣称任务恢复完成。

明确队列采用至少一次投递，并通过业务幂等处理重复消息。持久化任务创建与投递之间的缺口可通过 outbox 等机制处理；租约需考虑续期、失效及旧 Worker 的过期写入。为 PR 创建和评论发布建立操作标识及结果核对，处理“请求成功、响应丢失”的不确定状态。

验收：执行中终止 Worker 后任务可以接管或明确失败；重复投递不会重复发布 PR／评论；过期 Worker 不能覆盖新 Worker 状态。不要轻易承诺端到端 exactly-once。

### 第四步：建立真正独立的审查链路

将现有 findings 和评论工具扩展为独立 Reviewer。输入固定为 base/head SHA、diff 与相关上下文；输出包含位置、风险、依据和建议。校验行号属于当前 diff、去除重复 findings，并允许人工接受／拒绝。

验收：用人工标注样本评估有效缺陷率、召回情况与误报；Reviewer 没有源码写入权限；审查反馈能关联到对应版本，避免 PR 更新后位置失效。

### 第五步：再投入上下文和流式性能优化

先记录重复文件读取、输入 Token、工具输出体积和上下文截断问题，再选择仓库摘要、符号定位或混合检索。不要为了技术栈好看直接增加向量库。

流式层从周期全量快照逐步迁移为带 run_id、event_id 的增量事件，支持断线游标、有限重放和事件保留期。

验收：相同任务集、相同模型预算下，比较成功率、成本与延迟；浏览器断线后能恢复事件且不重复展示；旧仓库摘要能随提交变化失效。

## 6. 如何补上真正有价值的指标

| 指标 | 建议口径 | 避免的误导 |
|---|---|---|
| 端到端成功率 | 在规定时间和预算内通过预设验收的任务数／全部任务数 | 把创建 PR 或模型自评当成成功 |
| 首次成功率 | 第一轮运行即通过验收的任务数／全部任务数 | 将多轮人工修正后的成功计入首次成功 |
| 耗时 | 同时报告所有运行耗时和成功任务耗时，必要时区分排队／执行，给出中位数与 P95 | 只统计最快的演示样例 |
| 每成功任务成本 | 评测全部运行成本（含失败与重试）／成功任务数；另报每次尝试成本 | 只统计成功任务最后一次调用 |
| 故障恢复 | 注入指定故障后达到预定义正确终态的次数／故障注入次数，另核对重复外部写操作 | 用 Checkpoint 文件存在证明恢复成功 |
| 审查有效性 | 人工确认有效的 findings／全部 findings；有完整标注时计算召回率 | 只展示找到了多少条问题 |

结果句模板：

> 在固定模型、工具预算与仓库基线的【N】个内部任务上，将端到端验收通过率由【A%】提升至【B%】，每成功任务成本降低【C%】，并通过【M】次 Worker 故障注入验证恢复与重复发布防护。

括号必须以实测数据替换。不满足口径时删去该项；内部任务集不能写成 SWE-bench 等公开基准成绩。模型具有随机性，比较时保留原始运行记录，条件允许时重复运行，不挑选最好的一次。

## 7. 面试讲解与个人贡献

当前版本的 60 秒介绍模板：

> 这个项目面向代码仓库的开发任务，我基于课程项目完成了〔实际改造内容〕。系统用 FastAPI 接收需求，通过 DeepAgents 组织文件、命令和 Gitee 工具，先输出方案，用户确认后进入编码与验证流程。我重点做的是〔选择两项实际贡献〕，例如把工具错误转换成模型可以继续处理的反馈，以及把图状态和业务事件分开持久化。当前版本采用本地执行与 SQLite，我清楚它在隔离、取消和故障恢复方面的边界，下一步会通过〔真实已排期方案〕补齐，并用固定任务集验证收益。

准备回答的关键问题：

1. **框架已经做了什么，你做了什么？** DeepAgents 提供规划／文件工具／子 Agent 等框架能力；个人贡献应落到具体 Backend、Middleware、业务编排、协议适配或评测改造上。
2. **为什么同时存在 Checkpoint 和业务 Store？** 前者恢复图状态，后者服务任务查询与产品展示；当前业务 Store 不是自动具备语义记忆能力的知识库。
3. **模型判断“只读”是否足够？** 不够。分类选择流程，授权必须在实际操作路径上执行；Prompt 只能补充行为约束。
4. **同仓库两个任务同时开发怎么办？** 当前共享工作区存在冲突风险；目标方案是独立 worktree／执行环境，再对共享发布资源做必要协调。
5. **为什么不能把 SQLite 并发测试说成高并发平台？** 当前脚本用 12 个线程写入 120 条事件，验证范围是特定数据库访问路径，不代表 120 个并行 Agent，也不代表跨进程或集群能力。本次未运行该脚本。
6. **异常转成 ToolMessage 后一定能恢复吗？** 不一定。只是让模型获得可操作反馈；仍需错误分类、重试预算和测试证据来证明具体场景的恢复效果。
7. **创建 PR 后服务崩溃，再运行会怎样？** 当前代码有从部分错误响应返回已有 PR 的处理，但这不等于完整幂等协议；增强版需要业务操作记录与远端结果核对。

建议保留一页贡献清单：课程原始能力、自己修改的文件、对应问题、修改前后行为、验证证据。前端复用可以如实说明；后端可靠性改造仍然可以成为项目的核心价值。
