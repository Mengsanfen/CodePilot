# SQLite 数据存储迁移方案

## 一、需求理解

当前项目使用两个 JSON 文件持久化数据：

- **`users.json`**：用户数据（`username`、`password`、可选 `department_id`）
- **`departments.json`**：部门数据（`id`、`name`）

**目标**：将数据存储从 JSON 文件切换为 SQLite 数据库，同时对上层业务逻辑（路由、模板）**零改动**。对 `requirements.txt` 仅增加标准库无需新增依赖（Python 内置 `sqlite3`）。

**动机**（假设）：
- 当前模式下多次全量读写 JSON 效率低
- 缺乏并发写入保护
- 后续扩展复杂查询（如连表统计）困难

## 三、数据结构、接口或页面变化

### 3.1 SQLite Schema

```sql
-- 部门表
CREATE TABLE IF NOT EXISTS departments (
    id   INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT    NOT NULL UNIQUE
);

-- 用户表（预置初始测试账号）
CREATE TABLE IF NOT EXISTS users (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    username      TEXT    NOT NULL UNIQUE,
    password      TEXT    NOT NULL,
    department_id INTEGER,
    FOREIGN KEY (department_id) REFERENCES departments(id) ON DELETE SET NULL
);

-- 初始种子数据
INSERT OR IGNORE INTO departments (name) VALUES ('技术部');
INSERT OR IGNORE INTO departments (name) VALUES ('产品部');
INSERT OR IGNORE INTO departments (name) VALUES ('运营部');
INSERT OR IGNORE INTO users (username, password, department_id) VALUES ('admin', '123456', NULL);
```

**关键设计决策**：
- `department_id` 设为 `INTEGER`，允许 `NULL`（对应旧版"未分配"）
- `ON DELETE SET NULL`：部门被删除时用户不会被清除，只是脱绑
- `AUTOINCREMENT`：ID 自动管理，不再需要 `_next_department_id`
- `UNIQUE` 约束：用户名唯一、部门名唯一，由 SQLite 保证

### 3.2 数据库文件名

- `users.json` → `.data/app.db`（SQLite 单文件）
- `departments.json` → 废弃（可通过迁移期读取并导入）

选择 `.data/` 目录便于 `.gitignore` 忽略数据文件。

### 3.3 关键函数改造对照

| 旧函数 | SQLite 等效实现 | 性能提升 |
|--------|----------------|---------|
| `_load_users()` | `SELECT username, password, department_id FROM users` | 全量查询 |
| `_save_users(users)` | 不再整表覆写，改为 `INSERT/UPDATE` 逐条 | — |
| `_authenticate(name, pwd)` | `SELECT ... WHERE username=? AND password=?` | O(n)→O(1) |
| `_get_department_name(id)` | `SELECT name FROM departments WHERE id=?` | O(n)→O(1) |
| `_build_departments_with_count()` | `JOIN` 单次查询 | 2次全量IO→1次SQL |
| `_next_department_id()` | **删除**，SQLite AUTOINCREMENT 接手 | — |
| `_ensure_departments_file()` | `CREATE TABLE IF NOT EXISTS` + 种子数据 INSERT | — |
| 注册检查用户名冲突 | Python 扫描 → `SELECT EXISTS(...)` | O(n)→O(1) |

### 3.4 页面变化

**零变化**。所有模板不变。路由函数的返回值结构不变（仍是 dict），对 Jinja2 模板完全透明。

## 四、具体实施步骤

### 步骤 1：新增依赖与配置（10 分钟）

1. `requirements.txt` 无需新增（`sqlite3` 内置）
2. 在 `main.py` 顶部新增常量：
   ```python
   import sqlite3
   DB_FILE = ".data/app.db"
   ```
3. 新增数据库初始化和连接管理函数：
   ```python
   def _get_db() -> sqlite3.Connection:
       conn = sqlite3.connect(DB_FILE)
       conn.row_factory = sqlite3.Row  # 让结果支持 dict-like 访问
       conn.execute("PRAGMA journal_mode=WAL")
       conn.execute("PRAGMA foreign_keys=ON")
       return conn

   def _init_db() -> None:
       os.makedirs(".data", exist_ok=True)
       conn = _get_db()
       conn.executescript("""
           CREATE TABLE IF NOT EXISTS departments (...);
           CREATE TABLE IF NOT EXISTS users (...);
           INSERT OR IGNORE INTO departments (name) VALUES ('技术部'),('产品部'),('运营部');
       """)
       conn.commit()
       conn.close()
   ```

### 步骤 2：逐函数替换数据操作层（45 分钟）

这是核心步骤，建议按以下顺序逐个替换并测试：

1. **`_init_db()`** → 应用启动时调用，替换 `_ensure_departments_file()`
2. **`_load_departments()`** → `SELECT id, name FROM departments ORDER BY id`
3. **`_save_departments()`** → 对外接口保留但对内改为逐条 INSERT（新增部门）
4. **`_load_users()`** → `SELECT username, password, department_id FROM users`
5. **`_save_users()`** → 保留接口但改为 INSERT（注册）和 UPDATE（修改密码）分离
6. **`_get_department_name()`** → 单次 `SELECT name FROM departments WHERE id=?`
7. **`_build_departments_with_count()`** → 一次 SQL JOIN：
   ```sql
   SELECT d.id, d.name, COUNT(u.id) AS member_count
   FROM departments d
   LEFT JOIN users u ON u.department_id = d.id
   GROUP BY d.id
   ORDER BY d.id
   ```
8. **`_authenticate()`** → `SELECT * FROM users WHERE username=? AND password=?`
9. **删除 `_next_department_id()`**，AUTOINCREMENT 替代
10. **路由层改动**（最小化）：
    - `register_submit`：不再 `users.append()`，改为直接 `INSERT INTO users`
    - `modify_submit`：不再 for 循环替换，改为 `UPDATE users SET password=? WHERE username=?`
    - `delete_submit`：不再列表推导过滤，改为 `DELETE FROM users WHERE username=?`
    - `department_add`：不再 `deps_raw.append()`，改为 `INSERT INTO departments (name) VALUES (?)`
    - `department_users`：改为 SQL 查询
    - `department_query_submit`：改为 SQL 查询
    - `_add_query_history`：保持不变（内存存储）

### 步骤 3：更新测试文件（40 分钟）

所有测试文件的 `_init_users()` / `_init_deps() / setup_module / teardown_module` 从 JSON 文件操作改为 SQLite 操作：

```python
def setup_module():
    # 用临时数据库
    main.DB_FILE = ".data/test_app.db"
    main._init_db()
    conn = main._get_db()
    # 清空并注入测试数据
    conn.execute("DELETE FROM users")
    conn.execute("DELETE FROM departments")
    conn.execute("INSERT INTO departments (id, name) VALUES (1, '技术部'), (2, '产品部')")
    conn.execute("INSERT INTO users (username, password, department_id) VALUES "
        "('alice', '123456', 1), "
        "('bob', 'bobpass', 1), "
        "('carol', 'carpass', NULL)")
    conn.commit()
    conn.close()
    ...
```

关键点：
- 每个测试模块用独立数据库 `test_app.db`（例如 `test_department.db`）
- `teardown_module` 删除数据库文件
- 可以编写共享的 `conftest.py` 减少重复代码（建议）

### 步骤 4：清理旧文件与无关注释（10 分钟）

- 删除 `USERS_FILE`、`DEPARTMENTS_FILE` 常量
- `.gitignore` 新增 `.data/`

## 六、风险点与需要用户确认的事项

### 风险点

| 风险 | 严重度 | 缓解方案 |
|------|--------|---------|
| **迁移过程暂时 broken window** | 中 | 分步 commit，每个函数替换后立即验证测试 |
| **并发写入冲突** | 低 | WAL 模式 + `timeout=5` 连接参数缓解 |
| **数据迁移丢失** | 低 | 当前无持久生产数据；如果有，需编写迁移脚本读取 `users.json`/`departments.json` 导入 SQLite |
| **SQLite 不支持的字段扩展** | 低 | 当前用户只有 3 个字段，后期扩展用 `ALTER TABLE ADD COLUMN` 友好 |
| **测试隔离** | 低 | 测试用独立数据库文件，测试结束后清理 |

### 需要用户确认的事项

1. **数据库文件路径**：建议 `.data/app.db`（隐藏目录，不污染根目录）。可以改为 `app.db` 放在根目录吗？
2. **是否需要编写 JSON→SQLite 数据迁移脚本**？即首次运行时自动读取 `users.json` 和 `departments.json` 导入数据库。
3. **删除部门的级联行为**：当前 `ON DELETE SET NULL`，即删除部门后用户保持存在但变为"未分配"。是否需要改成阻止删除有用户的部门？
4. **密码存储**：当前为明文存储。迁移 SQLite 后是否需要顺便做密码哈希（`hashlib`）？这不影响本次迁移范围但影响数据安全。
5. **单测重复代码**：所有测试模块的 `setup_module` 有大量重复的数据准备。是否授权在迁移过程中新建 `conftest.py` + `fixtures` 统一管理？
